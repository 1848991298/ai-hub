# 按业务分批提交

使用用户的语言，遵循目标项目已有规则和提交格式。仅修改本技能时，不启动其他项目的提交流程。

## 1. 核对仓库与变更

确认实际仓库根目录、工作区、分支、上游、远端、近期提交及 worktree 关系；不要从目录名推断仓库归属。独立读取可并行执行：

```bash
git status --short
git diff
git diff --cached
git log -8 --oneline
git branch --show-current
git rev-parse --abbrev-ref --symbolic-full-name '@{upstream}'
git remote -v
git worktree list --porcelain
```

无上游或远端时如实说明。检查相关未跟踪文件，但不回显凭据；不切换有未提交改动的工作区，不覆盖其他任务成果。Git 地址含凭据时，展示前脱敏。

## 2. 按业务拆批

将同一业务的实现、必要平台接入及测试放在一批，按依赖关系排序；不要机械地按文件类型或平台拆成重复提交。

一次展示所有建议批次，每批包含：

- 完整文件路径、已暂存／未暂存／未跟踪状态和改动摘要。
- 同文件跨批时各批对应的改动片段，以及前置依赖。
- 完整提交说明，遵循项目格式；没有项目约定时采用简洁标题和必要的问题、方案说明。
- 多平台业务的链路结论及实际验证边界。

集中列出排除内容及原因：凭据、个人配置、本地日志、构建产物、其他任务改动和未获授权的内容。公开分发使用审核后的白名单，不把个人维护仓库的文件或历史整批推入公开仓库。

## 3. 核对多平台实际链路

本批涉及跨平台业务或声称多端复用时，必须在提交确认前核对受影响平台；单平台项目不强加此步骤。

- 从各平台实际入口追踪到桥接／适配、共享服务、接口、模型和缓存，检查注册、调用方及平台条件分支。
- 判定为共用、某平台独立、共享与平台实现混合或待核实，并给出关键文件或调用路径。
- 原生界面不同不代表业务流程独立；同一分支或共享目录也不证明各端入口均已接入。
- 发现不同服务、接口、数据口径或漏接入口时，说明差异与影响，不擅自扩大修复或提交范围。
- 分别记录共享测试、各平台检查／构建／装机／真机验收。一端或共享测试通过不能写成所有平台验收通过。

多条链路可用以下表格，简单情况用一段话说明：

| 本批业务链路 | 实现归属 | 各平台入口及调用依据 | 已验证与待验 |
| --- | --- | --- | --- |

只审查本批受影响链路，不因此启动全仓库重构或额外平台适配。

## 4. 明确授权与执行位置

提交前说明工作区绝对路径、准确分支、项目、托管平台和仓库归属，以及拉取来源；需要合入或推送时，同时说明准确目标分支和范围。

例如：`feature/example（示例项目 · GitHub：organization/repository）`。示例名称不作为默认配置；不能猜测主线为 `main` 或 `master`。

先展示可审核方案，再取得所需确认。用户此前已明确授权且覆盖相同文件范围、目标和操作时，直接复用授权，不重复询问；笼统的“整理提交”不自动授权推送或合入。支持全部批次、指定批次、逐批确认及只看方案。没有完整展示且未明确授权的批次不执行。

独立分支合入时，区分“仅本轮提交”和“来源分支全部独有提交”，已有独有提交不顺带合入。更换工作区或分支前说明原因与改动保护方案，并遵循用户及项目的授权要求。

## 5. 同步后提交

在已确认仓库和同步基准上执行：

1. 重新检查分支、上游、暂存区及工作区，先 fetch，核对远端新增提交与本地改动的重叠。
2. 可快进时使用 `git pull --ff-only <remote> <branch>`；分叉时说明显式整合策略并遵循授权，不反复执行未指定策略的 pull，不擅自改写历史。
3. 保护现有成果。确需暂存本任务改动时只保存明确范围，包含相关未跟踪内容并保留原暂存状态；恢复成功前保留可恢复副本，不自动全量 stash。
4. 解决冲突并完成必要检查；拉取、恢复失败或提交关系不明时停止后续提交、合入和推送。
5. 同步后重新检查批次差异与平台链路结论。远端已有相同或等价修改时去重；已提交但未推送的复用现有提交。
6. 若同步改变已确认的内容、范围、提交说明或平台业务行为，重新展示受影响部分并按需确认；未受影响部分不重复确认。

没有远端时可按授权本地提交；推送前必须明确目标仓库及分支。

只暂存本批明确文件或片段，不使用 `git add .`。暂存区已有其他任务内容时先隔离提交范围，不能一并带入。用暂存差异核对实际内容，并以 HEREDOC 或消息文件提交，避免 shell 转义改变提交说明：

```bash
git commit -F - <<'EOF'
feat: 简要说明本批业务变化

说明问题、方案及必要的验证信息，格式遵循项目约定。
EOF
```

每批完成后读取新提交内容和工作区状态，记录哈希，再执行下一批已确认提交。hook 失败时保留现场并定位原因，不擅自跳过 hook、修改业务内容或重复提交成功批次。新增或变化的未授权内容不自动纳入。

## 6. 合入、推送与回执

仅执行明确授权的合入及推送：

- 目标分支已在其他 worktree 检出时，使用该工作区并保护其改动；先同步目标远端，再按已批准范围整合。
- 可快进时优先快进；需要 merge 或 cherry-pick 时采用与批准范围一致的策略，不夹带其他提交。
- 每次 push 前重新核对分支、上游和工作区，fetch 并整合最新远端。若远端变化影响验证结论，先完成必要复验。
- 推送被拒绝时停止，重新核对并整合，不用强推或丢弃改动绕过分歧。
- 推送后读回远端提交号并检查领先／落后数量；远端同步和工作区是否干净分别报告。

不擅自修改 Git 配置，不用 `reset --hard` 覆盖成果；不擅自使用交互式暂存／rebase、`--amend`、`--no-verify` 或强制推送。合入和推送不自动授权发布、群消息、删除分支或移除 worktree。

最终回执列出执行工作区、分支与仓库归属、各批哈希、验证结果、合入／推送状态及保留的改动。多平台项目同时简述共享与独立部分、各平台实际验证及待验，不把源码核对、测试、装机和业务验收混为一谈。
